# Provider evidence — 2026-09-29

Evidence was gathered on September 28–29, 2026. Initial direct Meta requests returned HTTP 429 or an inaccessible-page error. The official pages subsequently loaded in the in-app browser and were read there. User-pasted Graph changelog content established v26.0. Pasted summaries were treated as leads, not as independent API authority. No private account API calls were made.

Required requested scopes: `instagram_business_basic`, `instagram_business_manage_comments`, `instagram_business_manage_messages`, `instagram_business_manage_insights`. Old `business_*` names are not used. The broad overview’s scope list is incomplete for insights; the endpoint-specific Insights documentation is the evidence for that permission.

The Instagram Login private-reply method is deliberately separate from normal DM sending. The initial pasted Facebook/Page-token private-replies page describes a different login family and is not the implementation contract.

Rate policy: reserve at most 700 sends in a rolling hour and five in a rolling second per connected account, across both automated send types. This is DMFlow’s conservative pilot budget, not a claim that Meta imposes those exact limits. Honor numeric Retry-After and rate-limit errors; bounded retry only after confirmed rejection. Ambiguous POST network failures remain uncertain. Other apps using the same account can still consume provider limits.

## Cloudflare evidence

[Queues delivery guarantees](https://developers.cloudflare.com/queues/reference/delivery-guarantees/) specify at-least-once delivery. Unique events, one-message-per-event constraints, transactional cooldown reservation, and atomic dispatch claims are therefore required even with Queues.

[D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/) executes statements transactionally. The local SQLite repository implements equivalent transactions. [Workers best practices](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/) informed quick webhook ACK, durable intake, bounded work, redacted structured logs, and secret bindings. CLI/config flags were checked against the installed Wrangler version and schema.

## TikTok — research only

The official [Business Messaging education hub](https://business-api.tiktok.com/portal/bm-api/education-hub) describes authorized business-account messaging. The official [API for Business documentation](https://business-api.tiktok.com/gateway/docs/index?identify_key=c0138ffadd90a955c1f0670a56fe348d1d40680b3c89461e09f78ed26785164b&language=ENGLISH) index lists Business Messaging access, automatic messages, review/privacy/security sections, comment events, capability checks, and **Comment-to-Message**. Therefore this capability is not described as nonexistent.

Exact regional eligibility, partner versus self-service access, and account-specific review requirements could not be established from the accessible documentation content. The browser’s Business Messaging detail link (`portal/docs?id=1832183871604753`) rendered the generic About the Guide page instead of the requested detail; the gateway menu also exposed hidden/non-actionable detail entries. Do not infer universal availability to an ordinary creator. TikTok stays explicitly unsupported in V1; verify region, authorized account eligibility, reviews, and per-account capabilities before enabling it in a later release.

## What this evidence does not prove

Documentation verification establishes request contracts. It does not prove that a particular Meta app has permission, that its webhook subscriptions are active, that production delivery succeeds, or that a creator’s metrics are returned. Those require the real-account acceptance run in `ACCEPTANCE.md`.
